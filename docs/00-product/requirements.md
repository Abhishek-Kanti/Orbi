### 1.2 Deterministic Task Management (`FR-TM`)

| ID | Status | Requirement | Principle(s) | Target Module(s) |
| :--- | :--- | :--- | :--- | :--- |
| **`FR-TM-01`** | `[CONFIRMED]` | **Durable Task State Machine**: Every accepted user request or automation dispatch shall materialize as a persistent Task record in PostgreSQL governed by a deterministic finite state machine (`CREATED`, `QUEUED`, `RUNNING`, `SUSPENDING_FOR_USER` *(crash-safe pre-checkpoint preparation state)*, `WAITING_FOR_USER` *(covering `INFORMATION_REQUEST`, `APPROVAL_REQUEST`, `SECURE_INPUT_REQUEST`, `HUMAN_TAKEOVER`, and `PHYSICAL_ACTION_REQUEST`)*, `COMPLETED`, `FAILED`, `CANCELLED`, `CANCELLED_AFTER_EXTERNAL_COMMIT`, `EXPIRED`). | `AP-03`, `AP-07` | `MOD-03` |
| **`FR-TM-02`** | `[CONFIRMED]` | **Queue-Driven Asynchronous Execution**: The Task Manager shall dispatch runnable task steps and harness work via Redis queues so long-running or blocked operations do not stall ingress channels and suspended tasks release workers completely with zero live waiting LLM sessions. | `AP-03`, `AP-09` | `MOD-03` |
| **`FR-TM-03`** | `[CONFIRMED]` | **Strict Isolation from Reasoning State**: Task lifecycle state, step counters, retry policies, interaction lifecycle, and approval bindings shall be owned exclusively by the Task Manager in PostgreSQL and must never rely on LangGraph internal memory or checkpoints as the source of truth. | `AP-03` | `MOD-03`, `MOD-04` |
| **`FR-TM-04`** | `[CONFIRMED]` | **Configurable Execution Budgets & Deadlines**: Tasks shall enforce deterministic, configurable guardrails—including maximum step counts, wall-clock timeouts, per-task/daily LLM token/cost budgets (`ADR-003`), and retry limits—and transition deterministically upon breach. | `AP-03`, `AP-08` | `MOD-03` |
| **`FR-TM-05`** | `[CONFIRMED]` | **Idempotent Pause & Action-Bound Resume on Approval**: When a task pauses via two-phase suspension (`SUSPENDING_FOR_USER` -> checkpoint save/read-verify -> `WAITING_FOR_USER` + `APPROVAL_REQUEST`), `MOD-03` (`HumanInteractionManager`) shall persist an immutable `ApprovalRequest` linked to an `InteractionRequest` bound to the exact action digest (`FR-GW-07`, `ADR-004`). Resuming execution via `task_lifecycle_outbox` (`RESUME_TASK`) and bounded-lease + `claim_epoch`-fenced `resume_token_id` claims (recovering expired `RUNNING` leases with `task_lifecycle_processed_events` / `step_execution_receipts` idempotency) shall verify responder identity pre-mutation (`403 AUTHZ_DENIED` leaves pending state intact), expiration, task/automation generation, and digest match (separating explicit `REJECTED` from drift `INVALIDATED`). Ordinary `INFORMATION_REQUEST` answers never count as approval. | `AP-06`, `AP-07` | `MOD-03`, `MOD-08` |
| **`FR-TM-06`** | `[CONFIRMED]` | **Centralized 5-Type Human-in-the-Loop Lifecycle & Crash-Consistent Checkpoint Resumption**: `MOD-03` (`HumanInteractionManager`) shall centrally manage persistent interaction requests via pre-mutation OpenFGA check (`403 AUTHZ_DENIED` leaves pending state intact), idempotent retry lookup, and a 3-step `interaction_version` CAS protocol (`CREATED -> PENDING_USER | TAKEOVER_ACTIVE -> RESPONSE_RECEIVED (v+1) -> VALIDATING (v+2) -> RESOLVED | VALIDATION_FAILED_RETRYABLE | REJECTED | INVALIDATED | CANCELLED (v+3)`, plus `EXPIRED`, `FAILED`, `ESCALATED`) across all 5 interaction types (`INFORMATION_REQUEST`, `APPROVAL_REQUEST`, `SECURE_INPUT_REQUEST`, `HUMAN_TAKEOVER`, `PHYSICAL_ACTION_REQUEST`). Task suspension executes two-phase checkpoint-first commit (`SUSPENDING_FOR_USER` -> save/verify `pending_checkpoint_id` -> `WAITING_FOR_USER` + `task_lifecycle_outbox`) and reconciler recovery covering expired `RUNNING` `RESUME_TASK` leases via `claim_epoch` fencing, post-resume crash-before-ack idempotency, write-ahead `DISPATCHING -> UNKNOWN_OUTCOME` receipt reconciliation, and `UNCERTAIN_EXECUTION_RECONCILIATION` human escalation (zero sleeping workers, `HITL-EVAL-01`–`26`, `DOC-HLD-002` §E.5). | `AP-02`, `AP-03`, `AP-07` | `MOD-03`, `MOD-04`, `MOD-09`, `MOD-18` |

### 1.4 Tool Registry, Tool Execution Gateway & Authorization (`FR-GW`)

| ID | Status | Requirement | Principle(s) | Target Module(s) |
| :--- | :--- | :--- | :--- | :--- |
| **`FR-GW-01`** | `[CONFIRMED]` | **Central Tool Registry**: Every callable tool and published skill wrapper shall be registered in a Central Tool Registry with versioned JSON Input/Output schemas, target harness/isolation tier, idempotency semantics (`idempotent`, `external_idempotency_mode: PROVIDER_IDEMPOTENCY_KEY | RECONCILABLE_READ_PROBE | NON_IDEMPOTENT_NO_RECONCILE`, `idempotency_window_seconds`, optional `reconciliation_probe_tool_id`), and a mandatory risk tier (`READ_ONLY`, `LOW_RISK_WRITE`, `SENSITIVE_WRITE`, `IRREVERSIBLE`). | `AP-01`, `AP-06` | `MOD-07` |
| **`FR-GW-02`** | `[CONFIRMED]` | **Single Tool Execution Chokepoint**: 100% of tool executions—across SaaS APIs, Playwright browser actions, sandboxed skill scripts, Windows Companion commands, and future IoT calls—shall route through the Tool Execution Gateway. | `AP-01` | `MOD-08` |
| **`FR-GW-03`** | `[CONFIRMED]` | **Externalized Household-Extensible OpenFGA Enforcement**: Before dispatching any tool or exposing sensitive memory/resource scope, the Gateway shall query OpenFGA (`MOD-09`) outside the LLM using deterministic subject, ownership/household, agent, tool, and target resource tuples (`ADR-002`). Fail-closed on error or denial. | `AP-02`, `AP-10` | `MOD-08`, `MOD-09` |
| **`FR-GW-04`** | `[CONFIRMED]` | **Mandatory Human Approval, Write-Ahead Receipt & Pre-Dispatch Cancellation, Generation & `claim_epoch` Gate**: Any tool call classified as `SENSITIVE_WRITE` or `IRREVERSIBLE` (or escalated by OpenFGA policy / Decision Service risk signal) shall be blocked by `MOD-08` and routed to `MOD-03`'s `HumanInteractionManager` (`APPROVAL_REQUEST`). Gate 2 shall bind a stable `action_idempotency_key` anchored to the stable logical `execution_id` and `logical_step_id` (remaining strictly unchanged across worker crashes, lease recovery, `W1 -> W2` worker replacement, LangGraph checkpoint restoration, and task resumption/retries—never including worker IDs, `claim_epoch`, `attempt_count`, or recovery generations) and write-ahead receipt (`PREPARED -> DISPATCHING -> CONFIRMED_SUCCESS | CONFIRMED_FAILURE_* | UNKNOWN_OUTCOME`) enforcing byte-for-byte immutable arguments, target resource, and action identity across retries. Immediately prior to *every* action dispatch, `MOD-08` Gate 5 shall revalidate live task cancellation state (`status == RUNNING`, `cancellation_requested == false`, matching `task_version`, matching `claim_epoch`, `lease_expires_at > now()`, fencing expired workers with `STALE_CLAIM_EPOCH_FENCED`), active `automation.generation` (if automation-triggered), live OpenFGA `policy_version`, single-use approval token consumption, and commit `DISPATCHING` before transmission—acknowledging `claim_epoch` and approval consumption fence Orbi-side execution only and cannot undo/confirm already-transmitted external calls. Crashes leaving `DISPATCHING` / `UNKNOWN_OUTCOME` shall reuse `action_idempotency_key` (`PROVIDER_IDEMPOTENCY_KEY`), run `RECONCILABLE_READ_PROBE`, or prohibit blind automatic retry and escalate (`UNCERTAIN_EXECUTION_RECONCILIATION`); cancellation races after non-interruptible external sends must record `CANCELLED_AFTER_EXTERNAL_COMMIT` honestly. | `AP-06`, `AP-07` | `MOD-08`, `MOD-03` |
| **`FR-GW-05`** | `[PROPOSED]` | **Schema Validation & Credential Injection**: The Gateway shall strictly validate `ToolCallIntent` payloads against `MOD-07` JSON Schema and inject OAuth tokens, API keys, or single-use `SECURE_INPUT_REQUEST` `ephemeral_secret_handle` secrets inside the Gateway/Connector boundary so agents, LangGraph checkpoints, memory, audit logs, and skill scripts never observe raw credentials. | `AP-01`, `AP-02` | `MOD-08`, `MOD-12` |
| **`FR-GW-06`** | `[PROPOSED]` | **Result Sanitization & Size Bounding**: The Gateway shall normalize harness responses, strip leaked secret patterns (including ephemeral `SECURE_INPUT_REQUEST` values) or oversized payloads, and tag external untrusted content (e.g., email bodies, web DOM text, screen OCR) with provenance labels before returning observations to the agent. | `AP-01`, `AP-05` | `MOD-08` |
| **`FR-GW-07`** | `[CONFIRMED]` | **Immutable Action-Bound Approval Integrity**: Every approval grant shall bind cryptographically to the exact `(user_id, task_id, execution_id, tool_id, tool_version, canonical_arguments_hash, target_resource, policy_version, expires_at)` tuple (`ADR-004`). Any alteration to tool arguments, target resource, execution/task cancellation state, or policy version, or expiry of the TTL, invalidates the approval and requires a fresh human approval. | `AP-06`, `AP-07` | `MOD-03`, `MOD-08`, `MOD-09` |

| **`FR-MS-08`** | `[CONFIRMED]` | **Provider-Independent Query Understanding & Selective Activation**: Before memory retrieval executes, `MOD-10` shall run a provider-independent Query Understanding stage identifying intent, key entities, exact lexical terms, temporal constraints, graph-traversal utility, and which retrieval branches to activate—avoiding unnecessary LLM calls for straightforward queries (`ADR-008`). | `AP-08`, `AP-09` | `MOD-10`, `MOD-05` |

| **`FR-MS-10`** | `[PROPOSED]` `[EVALUATION REQUIRED]` | **Configurable Candidate Fusion (Initial: RRF) & Identity-Only Deduplication**: Because branch scores operate on incompatible scales, `MOD-10: Memory Manager` shall fuse authorized multi-branch lists via rank/calibrated fusion—initially proposed as **Reciprocal Rank Fusion (RRF)**—preserving multi-branch provenance and deduplicating **strictly by `memory_unit_id`** (`content_hash` shall never serve as an equivalence/merge key across scopes, timelines, or owners) (`ADR-008`, `EVAL-07`). | `AP-04`, `AP-08` | `MOD-10` |
| **`FR-MS-11`** | `[PROPOSED]` `[EVALUATION REQUIRED]` | **Configurable Provider-Independent Reranking**: `MOD-10: Memory Manager` shall support an optional, replaceable reranking stage evaluating fused candidates against the original query without requiring an expensive LLM call for every retrieval, enforcing configurable `candidate_limit` and `final_context_limit` bounds while preserving provenance and relevance metadata (`EVAL-07`). | `AP-08`, `AP-09` | `MOD-10` |
| **`FR-MS-12`** | `[CONFIRMED]` | **Mandatory Per-Branch Authz, Source-Level Graph Isolation & Pre-Fusion Tombstone Gate**: Every retrieval branch (vector, lexical, graph, bitemporal) shall enforce **both** OpenFGA authorization (`private_user`, `shared_tenant`, `custom_acl`) **and** the authoritative `orbi_memory` deletion/tombstone gate (`deletion_state == 'ACTIVE'` and zero active/completed tombstones—blocking stale `CogneeAdapter` hits during `PENDING_PROPAGATION` or `FAILED_REQUIRES_RECONCILIATION`) **before** candidates enter fusion, reranking, or LLM context. For graph nodes, edges, convergent shared/private entities, and multi-hop paths, every contributing `source_memory_unit_id` shall be independently checked for active state + OpenFGA permission with zero permission unioning and fail closed if provenance, tombstone state, or authorization cannot be verified (`ADR-008`, `DOC-HLD-001`). | `AP-02`, `AP-07` | `MOD-10`, `MOD-09` |
| **`FR-MS-13`** | `[CONFIRMED]` | **Hybrid Retrieval Quantitative, Bitemporal, Deduplication & Security Evaluation**: Memory retrieval quality and security shall pass `EVAL-07` measuring `Recall@K`, `Precision@K`, `MRR`, `NDCG@K`, PG FTS vs. Genuine BM25 parity, retrieval latency, reranking overhead, historical/bitemporal correctness (including combined system-time + valid-time point queries), `memory_unit_id`-only deduplication, convergent entity graph isolation, and $0.0\%$ authorization leakage (`MEM-EVAL-01`–`14`). | `AP-07`, `AP-08` | `MOD-10`, `MOD-09` |
| **`FR-MS-14`** | `[CONFIRMED]` *(Thresholds: `[PROPOSED]`)* | **Memory Resolution Lifecycle (`NEEDS_CLARIFICATION` HITL) & Explicit Memory Deletion (`MOD-10`)**: `MOD-10` shall separate factual succession (`valid_to` closed, prior fact preserved for `HISTORICAL` recall) and belief correction (`recorded_to` closed, `superseded_by` forward-linked, corrected `MemoryUnit` inserted) from **Explicit Memory Deletion** (*"Forget that..."*). Pending `NEEDS_CLARIFICATION` items remain isolated in `memory_resolution_candidates` (zero active retrieval visibility), trigger centralized `INFORMATION_REQUEST` prompts via `MOD-03` (`HumanInteractionManager`) -> `MOD-18` (`MOD-01`/`MOD-02`), commit `InteractionStatus.RESOLVED` atomically with `MEMORY_CLARIFICATION_DECIDED` (`idempotency_key = sha256(memory_candidate_id, interaction_id)`) in `orbi_app.task_lifecycle_outbox`, deliver idempotently to `MOD-10.submit_clarification_decision()` via `orbi_memory.memory_sync_processed_events` with bounded retries/`DEAD_LETTERED` quarantine and a periodic `RESOLVED` vs. `PENDING_CLARIFICATION` reconciler, and preserve `original_source_provenance` & `original_trust_tier` (`HITL-EVAL-23`). Explicit deletion executes a 9-step durable lifecycle (`REQUESTED -> PENDING_PROPAGATION -> COMPLETED | FAILED_REQUIRES_RECONCILIATION`), capturing a non-plaintext `deletion_dependency_manifest` **prior** to scrubbing plaintext/provenance, enforcing 4-branch pre-fusion tombstone suppression (`deletion_state != 'ACTIVE'`), recomputing/pruning derived graph sources via `memory_sync_outbox`, setting terminal `deletion_state = 'COMPLETED'` tombstones, emitting redacted `MOD-15` audit records, and documenting backup TTL/tombstone-replay limits (`MEM-RES-01`–`10`, `MEM-DEL-01`–`06`, `DOC-HLD-001` §5–§6). | `AP-04`, `AP-07` | `MOD-10`, `MOD-03`, `MOD-09`, `MOD-15`, `MOD-18` |
